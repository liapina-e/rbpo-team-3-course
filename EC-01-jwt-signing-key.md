# EC-01. Ключ подписи JWT в публичном репозитории

### Проверяемое утверждение

Система выполняет операцию от имени пользователя, подлинность которого подтверждена при входе, и только его; подтверждение аутентификации, которое система не выдавала,
отклоняется (SR-04).

Нарушение соответствует угрозе T-04: ключ подписи JWT записан в `appsettings.json`
и попадает в публичный репозиторий, после чего любой читатель репозитория подписывает
этим ключом токен с идентификатором другого пользователя и действует от его имени.
Решение D-03 требует, чтобы значение ключа жило вне репозитория, приложение не
стартовало без ключа, а в проверке токена были включены подпись, срок, издатель и
аудитория при сроке жизни токена 60 минут.

### Исходный сценарий и наблюдение

- **Объект и исходная версия:** `TempShare.Api`, commit `1220bfb` (ветка `main`).
- **Условия:** приложение запущено по инструкции раздела 10 `PROJECT.md` (`docker compose up -d`, `dotnet run --project TempShare.Api`);
  зарегистрированы два пользователя — `alice` (владелец файла) и `bob`. Публичный репозиторий доступен на чтение любому.
- **Шаги:**
  1. Открыть `TempShare.Api/appsettings.json` в публичном репозитории и прочитать
     значение `Jwt:Key` (`dev-only-insecure-key-change-me-32chars-min`).
  2. `alice` загружает файл и выдаёт `bob` разрешение, после чего `GET /api/files/{fileId}/recipients`
     показывает владельцу идентификатор получателя — `RecipientId` пользователя `bob`.
  3. Сформировать HS256-токен с утверждением `ClaimTypes.NameIdentifier`, равным
     идентификатору `bob`, подписав его прочитанным из репозитория ключом.
  4. Выполнить `GET /api/files/{fileId}/content` с этим токеном.
- **Фактический результат до изменения:** сервер принимает токен и выдаёт содержимое файла, то есть операция выполняется от имени `bob` без знания его пароля.
  Дополнительно наблюдается: `ValidateIssuer` и `ValidateAudience` в `Program.cs` выставлены в `false`, а срок жизни токена в `JwtTokenService` — 8 часов вместо 60 минут.

### Причина и изменение

- **Причина:** значение секрета подписи хранилось в версионируемом файле конфигурации
  `TempShare.Api/appsettings.json` и попадало в публичный репозиторий, а
  `Program.cs` принимал его без проверки наличия. Проверка токена опиралась только
  на подпись и срок: издатель и аудитория не проверялись. Поскольку идентификатор
  пользователя берётся из утверждения токена (D-02), знание ключа подписи
  обесценивает все последующие проверки прав — и D-01, и D-02.
- **Исправляющее изменение:**
  - значение `Jwt:Key` удалено из `appsettings.json`; в файле остались только
    `Jwt:Issuer` и `Jwt:Audience`
  - `Program.cs` читает ключ из конфигурации (переменная окружения `Jwt__Key`
    или `dotnet user-secrets`) и завершает запуск исключением, если ключ
    отсутствует или короче 32 байт
  - в `TokenValidationParameters` включены `ValidateIssuer` и `ValidateAudience`
    с явными значениями, `ClockSkew` ограничен одной минутой
  - `JwtTokenService` проставляет издателя и аудиторию и выдаёт токен на 60 минут
- **Проверенная исправленная версия:** commit `<10216d6c7c551f90a5470770f9d5e86eb7e163c1>`.

Ключ `dev-only-insecure-key-change-me-32chars-min` остаётся в истории Git и поэтому
считается скомпрометированным, он не используется как рабочий ни в одном окружении.

### Проверки и результаты

- **Негативная:** `Download_WithTokenSignedByWrongKey_Returns401`
  (`TempShare.Tests/AccessControlTests.cs`). Токен с идентификатором существующего
  пользователя, подписанный ключом, отличным от секрета сервера, предъявляется
  маршруту выдачи содержимого.
  Ожидаемый результат — `401`, содержимое не передаётся.
  Фактический результат: до изменения, когда секрет сервера совпадал со значением из
  репозитория, такой токен принимался и файл выдавался; после изменения — `401`.
- **Регрессионная:** `Download_WithServerIssuedToken_Works` и
  `Download_ByRecipientWithActivePermission_Returns200`. Штатный токен, выданный
  маршрутом входа, по-прежнему даёт владельцу и получателю с действующим разрешением
  ответ `200` с содержимым файла.
- **Проверка запуска без ключа:** запустить `dotnet run --project TempShare.Api`
  с неустановленной переменной `Jwt__Key`.
  Ожидаемый и фактический результат: приложение не стартует, в выводе —
  `Jwt:Key is not configured`.
- **Проверка текущей версии файлов:** `git grep -n "dev-only-insecure-key"` по рабочему
  дереву не находит значение ключа; оно присутствует только в истории коммитов.
- **Команда и условия выполнения:** `dotnet test` в корне репозитория, .NET SDK 8.0,
  проверки выполняются на EF Core InMemory без PostgreSQL и Docker.

### Вывод и границы

В проверенных условиях сервер не принимает токен, подписанный любым ключом, кроме
собственного секрета, и не стартует без заданного секрета, значение ключа отсутствует
в текущей версии файлов репозитория. Штатный вход и доступ владельца и получателя
с действующим разрешением сохранены.

Вне области проверки: безопасность хранения секрета в окружении запуска (переменные
окружения и `user-secrets` защищены средствами ОС, а не приложением), ограничение
числа попыток входа (SR-07, T-09) — отдельное требование, этой цепочкой
не закрытое, отзыв уже выданного токена до истечения его 60 минут не поддерживается,
поэтому смена ключа требует повторного входа всех пользователей.
