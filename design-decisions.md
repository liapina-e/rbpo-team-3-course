# Проектные решения безопасности

Решения закрывают приоритетный набор угроз T-01–T-05 из модели угроз (`threat-model.md`) и опираются на требования `security-requirements.md`. Менее приоритетные угрозы T-06–T-09 отмечены там, где решение закрывает их попутно. Стек и допущения — раздел 9 `PROJECT.md` и раздел «Модель продукта» модели угроз. Проверки ниже — план, они ещё не выполнены.

Решения описывают целевое состояние. Код на `main` уже реализует вычисление действующего разрешения (`Permission.IsActiveAt`), уникальный индекс разрешений со сбросом `revokedAt` при повторной выдаче, проверку владельца при выдаче и отзыве, хранение файлов под GUID и хеширование паролей BCrypt. Пока не реализованы единый `PermissionService` (проверки выполняются в контроллерах), вынос ключа из `appsettings.json`, проверка издателя и аудитории токена, срок токена 60 минут, проверка итогового пути и `FileMode.CreateNew` из D-04.

| Решение | Закрывает T | Требования SR |
| --- | --- | --- |
| D-01. Действующее разрешение вычисляется в момент запроса | T-01, T-02, T-06 | SR-01, SR-03 |
| D-02. Владелец и пользователь определяются сервером | T-03 | SR-02, SR-04 |
| D-03. Подпись токена и ключ подписи | T-04 | SR-04 |
| D-04. Файл хранится под именем, выбранным сервером | T-05 | SR-06 |

### D-01. Действующее разрешение вычисляется в момент запроса

**Контекст:** доступ к содержимому должен прекращаться точно в момент окончания срока или отзыва. Первоначальная идея: фоновая задача Quartz.NET раз в 5 минут переводит просроченные разрешения в состояние «истекло», а проверка доступа пропускает только состояние «действует». Пограничный случай из модели угроз показал, что в этом варианте получатель скачивает файл до 5 минут после окончания срока, а проверка, запускающая задачу перед запросом, подтверждает задачу, а не свойство SR-01.

**Решение:** в `PermissionService` один метод `HasActivePermission(fileId, userId)` вычисляет действующее разрешение в момент запроса: запись для пары `(fileId, userId)` существует, `revokedAt` пуст и `expiresAt > now`. Текущий момент передаётся параметром (`Permission.IsActiveAt(DateTime now)`, в работе — `DateTime.UtcNow`, в проверках — заданное значение). Метод вызывается во всех маршрутах, выдающих содержимое (`GET /files/{id}/content`, `GET /shared`, `GET /files/{id}`), других путей проверки нет. Поле состояния и задача Quartz.NET основанием для доступа не служат, задача может только удалять старые записи. На `(fileId, recipientId)` в базе действует уникальное ограничение: повторная выдача разрешения тому же получателю не создаёт вторую запись: она обновляет `expiresAt` существующей и сбрасывает `revokedAt`, поэтому владелец может вернуть доступ после отзыва. Для чужого файла без разрешения, как и для несуществующего, возвращается один и тот же ответ «не найден», чтобы идентификатор не подтверждал существование файла (SR-03).

**Обоснование:** свойство «после срока доступа нет» обеспечивается самим вычислением, а не изменением данных, поэтому окно между сроком и работой задачи исчезает. Уникальное ограничение исключает второе разрешение: отзыв одной записи закрывает доступ получателя полностью (T-06). Единственная точка проверки не даёт добавить маршрут без проверки.

**Связанные угрозы:** T-01, T-02, T-06 (попутно T-07, часть про метаданные файла).

**Связанные требования:** SR-01, SR-03.

**Альтернативы и выбор.** Сравнивались два способа обеспечить свойство «доступ прекращается в момент окончания срока»:

| | A. Состояние обновляет задача Quartz.NET | B. Вычисление при запросе (выбрано) |
| --- | --- | --- |
| Где решается доступ | поле `status` в базе | сравнение `expiresAt` и `now` в запросе |
| Окно после срока | до интервала задачи (5 минут), короче интервал — больше нагрузки | нет |
| Цена | дешёвая проверка при запросе | условие выполняется при каждом запросе, нужен индекс по `(fileId, recipientId)` |
| От чего зависит корректность | работа и расписание задачи | корректность часов хост-машины |
| Что видит владелец | состояние «истекло» в списке | то же, вычисляется при выдаче списка |

Допущения: один экземпляр сервера на одной машине (раздел «Допущения» модели угроз), число разрешений мало, поэтому проверка при запросе не создаёт заметной нагрузки. Граница применимости: решение верно, пока время берётся из одного доверенного источника. Условие пересмотра: если сервер запускается в нескольких экземплярах или часы хоста становятся ненадёжными, время нужно брать из СУБД (`now()` в запросе), а при большой нагрузке на проверку добавить кеш с коротким сроком, не больше допустимой задержки доступа после срока.

**Будущая проверка:**

- **Условие:** разрешение получателю B на файл A с `expiresAt = 12:00:00 UTC`, в `IsActiveAt` передаётся тестовое время, фоновая задача отключена.
- **Действие:** запросить содержимое от имени B при времени 11:59:59, затем при 12:00:00. Отдельно: выдать B два раза разрешение на один файл, отозвать, запросить содержимое; затем выдать разрешение заново. Отдельно: запросить файл A от имени C (без разрешения) и несуществующий идентификатор.
- **Ожидаемый результат:** в 11:59:59 содержимое выдано, в 12:00:00 отказ без запуска задачи, в `GET /shared` файла нет. После повторной выдачи в базе одна запись, после отзыва отказ, после новой выдачи доступ возвращается. Ответы для C и для несуществующего файла совпадают. Критерий SR-01 используется как есть.

**Ограничения и последствия:** корректность зависит от допущения о системных часах (раздел «Допущения» модели угроз); смещение часов хоста сдвигает момент окончания срока. Каждое чтение содержимого выполняет запрос к таблице разрешений.

### D-02. Владелец и пользователь определяются сервером

**Контекст:** все значения запроса формирует клиент (TB-1). Если сервер берёт идентификатор пользователя или владельца из тела запроса либо проверяет только наличие токена, посторонний выдаёт и отзывает разрешения на чужие файлы (T-03).

**Решение:** идентификатор пользователя берётся только из утверждения `ClaimTypes.NameIdentifier` проверенного токена (его кладёт `JwtTokenService`) и больше нигде. При загрузке `ownerId` файла записывается из токена, поле владельца в теле запроса игнорируется. В `POST` и `DELETE /files/{fileId}/permissions` перед изменением загружается файл, и операция выполняется, только если `file.ownerId == userId`; иначе отказ (для чужого файла — «не найден»). Продление — частный случай выдачи, поэтому действует то же правило. Проверка владельца находится в сервисном слое, а не в контроллере, чтобы её нельзя было обойти новым маршрутом.

**Обоснование:** границу доверия TB-1 пересекают только данные запроса, а владелец — свойство записи в базе, которое клиент изменить не может. Одно правило для выдачи, продления и отзыва закрывает все три сценария T-03.

**Связанные угрозы:** T-03.

**Связанные требования:** SR-02, SR-04.

**Будущая проверка:**

- **Условие:** владелец A с файлом, получатель B с действующим разрешением, постороннее C.
- **Действие:** от имени B выдать разрешение C на файл A и продлить своё; от имени C отозвать разрешение B; от имени C загрузить файл с `ownerId = A`.
- **Ожидаемый результат:** первые два запроса отклонены, набор разрешений и сроки не изменились, разрешение B действует; загруженный файл принадлежит C. Совпадает с критериями SR-02 и SR-04.

**Ограничения и последствия:** передача файла другому владельцу не поддерживается. Каждая операция с разрешением читает файл из базы.

### D-03. Подпись токена и ключ подписи

**Контекст:** если ключ подписи JWT лежит в `appsettings.json` публичного репозитория, посторонний подписывает токен для любого пользователя и обходит D-01 и D-02 (T-04).

**Решение:** ключ подписи не хранится в репозитории: задаётся переменной окружения `Jwt__Key` (в конфигурации ASP.NET Core это параметр `Jwt:Key`, имя в коде не меняется; при локальной разработке — `dotnet user-secrets`). В `appsettings.json` значения ключа нет, пример переменной — в разделе 10 `PROJECT.md`. Ключ — не короче 32 байт, подпись HS256. Приложение не стартует без ключа. Ключ разработки из истории коммитов считается скомпрометированным: рабочий ключ должен отличаться от него и нигде не переиспользуется. В `TokenValidationParameters` включены проверка подписи, срока (`ValidateLifetime`, `ClockSkew` не более 1 минуты), издателя и аудитории (значения `Jwt:Issuer` и `Jwt:Audience` задаются в конфигурации и совпадают при выдаче и проверке); срок жизни токена — 60 минут; пользователь определяется только из проверенного токена.

**Обоснование:** публичный репозиторий — требование курса, поэтому всё, что в нём лежит, известно постороннему; значение ключа должно жить вне репозитория. Симметричная подпись подходит, потому что токены выдаёт и проверяет один и тот же сервер. Проверка издателя и аудитории не даёт принять токен, выданный для другого сервиса тем же ключом.

**Связанные угрозы:** T-04 (попутно T-09: пароли уже хранятся хешем BCrypt, ограничение попыток входа решением не охвачено).

**Связанные требования:** SR-04.

**Будущая проверка:**

- **Условие:** запущенный API с рабочим ключом из переменной окружения, штатный токен пользователя A.
- **Действие:** отправить запросы с токеном, подписанным другим ключом, в том числе ключом разработки из истории коммитов; с изменённым после выдачи содержимым; с истёкшим сроком (в том числе через 2 минуты после окончания); запустить приложение без `Jwt__Key`; просмотреть текущие файлы репозитория на значение ключа.
- **Ожидаемый результат:** запросы с чужим, изменённым и истёкшим токеном отклонены, состояние файлов не меняется; без ключа приложение не стартует; в текущей версии файлов ключа нет. В истории коммитов ключ разработки остаётся, поэтому он не используется как рабочий, и токен, подписанный им, отклоняется.

**Ограничения и последствия:** каждый участник и каждое окружение запуска задаёт ключ сам. Утёкший ключ требует его смены и повторного входа всех пользователей. Переход на асимметричную подпись нужен, только если токены начнёт проверять другой сервис.

### D-04. Файл хранится под именем, выбранным сервером

**Контекст:** имя файла приходит от клиента через TB-1. Если путь записи строится из него, имя `../../appsettings.json` пишет за пределы каталога хранилища, а совпадение имён двух загрузок перезаписывает чужой файл (T-05).

**Решение:** на диске содержимое хранится под ключом `storageKey` — случайный GUID, выбранный сервером, без расширения, в каталоге хранилища. Исходное имя файла сохраняется только в записи базы (метаданные) и никогда не участвует в построении пути. Перед записью итоговый путь приводится к полному (`Path.GetFullPath`) и проверяется, что он начинается с каталога хранилища; при несовпадении запись отклоняется. Запись с `FileMode.CreateNew`: существующий файл не перезаписывается.

**Обоснование:** свойство «клиент не управляет путём» обеспечивается тем, что в путь не попадают данные клиента. Это надёжнее очистки имени от `..`, где легко пропустить кодировки и разделители ОС. Метаданные хранят имя, поэтому получатель видит его без изменений (SR-06).

**Связанные угрозы:** T-05.

**Связанные требования:** SR-06.

**Будущая проверка:**

- **Условие:** пустой каталог хранилища, `appsettings.json` рядом с приложением.
- **Действие:** загрузить файл с именем `../../appsettings.json`; загрузить два файла с именем `report.pdf` от разных владельцев и скачать каждый его получателем.
- **Ожидаемый результат:** `appsettings.json` не изменился, в каталоге хранилища появились файлы с именами-GUID; каждый получатель скачивает свой файл, в метаданных показано имя `report.pdf`. Совпадает с критериями SR-06.

**Ограничения и последствия:** содержимое на диске нельзя найти по имени без обращения к базе; при потере базы соответствие утрачено. Ограничения на размер и тип загружаемого файла решением не охвачены.

## Разрывы в приоритетном наборе

Цепочки T-01–T-05 → SR → D → будущая проверка прослеживаются целиком. Требования SR-01 (уточнение про срок без фоновых задач и несколько разрешений) и SR-04 (однозначный исход при чужом идентификаторе) уточнены в `security-requirements.md`, D-01 и D-02 им соответствуют. Остаётся:

- **Не приоритетные T-06–T-09:** T-06 закрыта уникальным индексом и сбросом `revokedAt` в D-01; T-07 частично закрыта D-01 и D-02, остальное — SR-03; T-08 (часовой пояс, SR-05) и T-09 (ограничение попыток входа, SR-07) отдельных решений пока не имеют, при необходимости добавляются D-05, D-06.
